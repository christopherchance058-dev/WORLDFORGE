# WORLDFORGE — project context

Read with [AGENTS.md](AGENTS.md). This is the compact architecture reference; [README.md](README.md) has user instructions and recovery procedures. Verify task-relevant source when changing behavior; this document is not evidence that tests currently pass.

## Purpose and workflow

A personal, local-first worldbuilding encyclopedia and interactive atlas. Favor connected lore and easy navigation over many empty categories. Do not invent established lore.

Workflow: write entries and short descriptions, organize categories, nest locations and link their inhabitants/history/factions, then place entry-linked pins on uploaded maps. Multiple independent worlds share one server. The sidebar has no world box. The Location category uses a house icon; Maps sits separately under Atlas, with its map icon. The workspace heading is Locations; internal `Locations` category keys and Geography modules are unchanged. The home banner has pencil (edit), two arrows (switch/create), and a top-right trash can (recoverable world deletion). New entry sits beside search/sorting; category navigation lives only in the sidebar. Added worlds start empty; the original library remains the default world. The browser remembers its last selection; already-open tabs keep their own world. No login, paid service, external API, or cloud storage is required. Cloud-workspace files live on that machine.

## Universal connection direction

Every category uses the shared `Connections.editor` and a single **Connections & linked lore** reading section. Existing Character/Creature/Magic arrays retain their owners; other categories/custom entries and eras use optional top-level `connections`. Shared rows retain `entryIds` and optional typed `eraIds`, open wording, neutral selection notes and linked description/history. Existing specialist fields retain their semantics and feed `Connections.structured`; never append category-specific backlink headings or duplicate facts. All rows use the same EntryProfile horizontal label badge / colored target-chip layout. Incoming provenance preserves the source's wording without inventing reverse facts. Narrative @ mentions are separate from explicit connections.

Future categories automatically get the generic editor/reader through app.js. Reuse this infrastructure and register any new specialist facts in the central adapter, with validation/search/navigation/deletion/backups. Characters and Creatures additionally offer optional manual, multiple `livedEraIds` with `livedEraNames` fallbacks and saved era timeline banners. This is recorded lore, not inferred lifespan/calendar arithmetic. Empty optional features stay hidden.

## Stack, commands and tests

- Plain HTML/CSS/browser JavaScript; Node.js **24+**, CommonJS server modules and built-in `node:sqlite`. No frontend framework or build step.
- Runtime dependencies: `sharp` validates/decodes images; `archiver` streams ZIP exports; `yauzl` reads/validates ZIP imports. Playwright is the test dependency.
- `npm ci`: install locked dependencies on first setup or after lockfile/dependency changes; unnecessary for every task when already installed.
- `npm start`: `node server.js`, default `http://localhost:3000`, bound to `127.0.0.1`. `PORT` overrides the port. Serve through Node, not by opening `index.html` directly.
- `npm test`: `playwright test`. Target an affected suite with `npx playwright test tests/geography.spec.js` (substitute the relevant suite).
- If `/usr/bin/chromium` exists, test configuration uses it; otherwise install Playwright Chromium with `npx playwright install chromium`. Unprepared Linux hosts may need `npx playwright install --with-deps chromium` (CI uses this).
- Tests import `tests/fixtures.js`: each library uses an OS temporary `worldforge-test-*` directory, its own server, an assigned port, and restart/cleanup helpers. The fixture overrides the config URL. CI uses Node 24/Chromium; configuration is not proof of a passing run.

## Data, compatibility and existing behavior

- Library root: `WORLDFORGE_DATA_DIR` or `data/` beside `server.js`. Contains `worldforge.sqlite`, possible `-wal`/`-shm` files, `images/`, `backups/` and `staging/`. Each Store also has an additive `world_appearance` table holding an optional managed banner image; missing appearance fields preserve the current banner for old clients/imports. Banner references participate in metadata revision checks, validation and ZIP image remapping. The original database also holds the additive `world_catalog` table (id/title/description/profile revision); added libraries live under `worlds/<generated UUID>/` with their own database, images, backups and staging. An additive `world_trash` table hides deleted worlds without removing their files; deletion checks both metadata/profile revisions and verifies a portable ZIP (manifest plus all image checksums) before hiding the world. The switcher can restore worlds or download deletion ZIPs; deleting the last active world creates an empty replacement. Trashed IDs reject API reads/writes with 410; unscoped legacy API requests are never redirected to another world. The browser bootstraps from the active catalogue, keeping legacy browser migration scoped to the original default world. Older app versions ignore Trash and may show those retained worlds again. The first catalogue creation on an initialized library makes and integrity-checks a `before-worlds-*.sqlite` snapshot; existing content tables are not rewritten. Default `data/` is Git-ignored but **real user data**, not disposable.
- Images are immutable files with generated filenames, `/api/images/<id>` references and SQLite metadata/checksums; not base64 localStorage or database blobs. Duplicate bytes can be reused. Limits: 50 MB / 80 million pixels per image; entries accept PNG/JPEG/WebP/GIF, map upload UI PNG/JPEG/WebP. Removed/cancelled images are retained and exported; no unused-image cleanup exists.
- **SQLite schema 5; API/ZIP format 6** (independent versions). Old clients cannot PUT earlier API formats. Schema 3/4 upgrades take a SQLite snapshot before transactional conversion. Geography adds optional `entry.location` JSON, not new tables or a separate database; old entries need no rewrite.
- Categories accept optional six-digit hex `color` metadata. An additive `category_colors` SQLite table stores overrides per world; existing category/entry records are not rewritten and schema/API/ZIP versions stay unchanged. Category settings offer 32 presets/custom color, default reset and Light/Dark previews. Existing deterministic fallback colors are preserved. Names/icons are chosen only at category creation; existing categories expose only color editing, including future custom categories. Previously saved names/icons remain unchanged. The world banner and its controls appear only on All entries. Missing colors use shared deterministic defaults; renaming in the current UI retains the chosen color. ZIP manifests carry the optional category property, including on restore; old colorless backups load with defaults. Older app releases omit colors from exports, so use this release for portable color backups. Only clickable entry references use category colors (destination category), through `CategoryColors.apply`; CSS selects contrast-adjusted shades per theme. Neutral label badges and faint row dividers reuse the shared reading fields. Future structured links must use the same helper; names/headings remain neutral.
- Entries include category name, title, description, optional `summary`, tags, year, image reference and timestamp. Magic/Creatures are included in customizable categories. History's specialized editor uses category `History` or an optional history payload. Keep unknown/older payload fields when editing.
- Shared **Description and Short description** support `@` selection across the current world. `descriptionReferences` / `summaryReferences` use `{version:1, items:[{token,entryId,label}]}` as optional entry JSON (no SQLite/API/ZIP version change). Tokens use escaped labels, URI-encoded stable IDs and unique UUID markers; only registered exact tokens render as references, so old/token-like text remains literal. Preserve this metadata when editing/backing up entries. Missing targets are allowed and show an unavailable fallback; render with DOM text APIs, never HTML. Specialist fields bind through `DescriptionLinks.bind(input, owner, key, {label,compact})` and collect through `collectFields`; optional owner-local `textReferences[key]` reuses the same v1 registry. Render specialist fields with `renderField` / `plainField`, validate known owners server-side, and keep repeated-row registries on each row (not numeric paths). Standalone pin descriptions remain plain. Saved v1 Description tokens are unchanged; editing renders removable noneditable chips with live names. Linkable fields share autocomplete with managed image URLs/category-icon fallback (no separate thumbnail endpoint exists). Cards use shared safe badge previews; linked pins reuse the source entry renderer, and deletion snapshots store readable plain text. Chip removal preserves adjacent text; insertion/paste checks each field’s existing serialized capacity (including 120-character short fields) without truncation. Rich HTML is never accepted from paste/drop. Undo/redo keeps up to 100 per-field snapshots. Copying raw tokens into another entry does not register them—use autocomplete there. Linking itself adds no browser-history integration or new backlinks; application Back/Forward is provided separately by `navigation.js`.
- Characters use optional `entry.character` JSON; no separate tables or migration. Title is the full name (blank UI saves as “Unnamed character”); shared description may be blank for Character and Location entries. `entry.image` remains the canonical primary portrait, including for linked map pins. Additional images live in `character.gallery` (up to 50 immutable image references/captions), covered by shared validation and backup remapping. Character links use entry IDs, expose backlinks, and clear deleted targets while retaining relationship notes/history. Dates/ages accept fantasy-calendar text; all deeper fields are optional. Character type/status are free text (legacy enum codes remain readable). Short identity/appearance/work fields suggest values from saved characters in the current world: linked compact fields use the shared autocomplete menu; unlinked fields retain native datalists. Shared `EntryProfile` headers/sections/field pairs now unify Characters, Factions and Locations (including category reading dialogs). Saved entries in every category open in the shared reading dialog over a blurred, retained browsing workspace. Read-only field labels align in a left column with values on the right (stacking at narrow widths); icon-only pencil/trash actions have accessible labels/tooltips, and tags use readable sizing; shared multiline metadata controls paragraph layout and whitespace-only fields/sections stay hidden. All entry browsers share rectangular cards with square thumbnails and Small/Medium/Large sizing (`worldforge.entry-card-size` in browser storage, with the old character-only preference read as a fallback; Compact maps to Small). All sizes use a square thumbnail beside title and tags, with the preview spanning the full width underneath. Cards omit category/year/species/occupation/status/location-type metadata rows; saved records and reading windows retain those details. No size-dependent tag relocation is used; cards keep natural heights rather than stretching to match neighbors. Image size, text space and preview lines scale together; captions never cover images. Profile portraits and entry-detail previews use bounded square frames with display-only centered cover cropping. Full-image links open untouched originals. Keep shared profile image sizing independent from listing-card styles. All profile section headings are larger than their body text; empty fields remain hidden. Shared editors reuse the Character image sidebar and collapsible sections with the existing narrow-form fallback. Geography keeps its hierarchy alongside a card overview. No image files or entry records are resized/reformatted. All entry portraits/emblems/illustrations and appearance-gallery previews recommend 1024 × 1024 (1:1), including Location illustrations. Square cover framing never changes original aspect ratio/bytes; primary and gallery images provide full-original links. Map image canvases and world banners keep their natural/wide proportions. Read-only linked-pin art previews are square; map backgrounds remain untouched.
- Factions retain shared title/description requirements; all specialist fields are optional in `entry.faction` JSON (no schema/archive change). Nine collapsed form groups cover identity, leadership, origins, purpose, territory, membership, diplomacy, resources and culture/secrets. The original shared image is the emblem (1024 × 1024 recommendation); no new image storage. `FactionModel.groups` declares 19 text fields, 15 linkable, with shared browser/server limits. Headquarters and territory IDs must resolve to locations; seven optional ID lists reuse existing selectors. Deletion cleans structured IDs but preserves written lore and unavailable @ references; incoming links produce Connected factions on referenced entries. Important members are highlights, not an automatic rewrite of Character faction affiliations. Category renaming preserves faction identity through its optional payload. Specialist text and linked names participate in shared search.
- Geography offers 12 preset location types plus custom free-text type/status values, optional grouped fields and ID-based links. Location identity is category `Locations` **or** a location object. Parents must be locations; cycles/missing targets are rejected. Deleting a parent moves direct children to its parent/top level, not cascading deletion. Other references are cleaned; travel notes retain former-destination labels. Limits: 64 hierarchy levels, 500 links/list, 100 travel rows; travel estimates are manual.
- Maps may start without images; ordered canvases each own their pins. Permanent pin coordinates are **normalized x/y in [0,1]**, relative to that image. Linked entries supply live titles/images/descriptions; entry deletion keeps standalone pin snapshots. Multi-upload, image management, fantasy symbols, hover previews, left reading panel, pan/zoom and optional browser fullscreen already exist.
- ZIP export covers only the selected world: `manifest.json` plus **all registered image files in that world**. An optional `world` profile is included without changing archive format 6; restore deliberately retains the destination world’s name/description. Export each world separately for portable backups, or stop the server and copy the entire root data folder to preserve the catalogue and every world. Restore validates records, paths, checksums/images and references, creates a rollback ZIP, then replaces records transactionally. Accepts ZIP 3–6 and legacy JSON arrays/versions 1–2; version 1 preserves current maps. Legacy browser key `worldforge.entries.v1` is migrated idempotently with original JSON/checkpoints preserved and the original browser value untouched.

- **All current entry categories:** shared Description and Short description support links, including Characters, Locations, History, Factions, Magic, Creatures and custom categories. Type/status remain plain classification values with learned datalist suggestions; founded date and membership size remain calendar/estimate text. Headquarters, leaders, founders, territory, important members, allies, rivals and related lore use stable-ID selectors instead of @ editors.
- **Geography specialist fields:** government, climate/environment, dangers/hazards, resources/trade goods and secrets; each travel row's method and notes. Linked map pins display the source entry's linked Description through the existing renderer; this does not enable linking in standalone pin text.
- **Intentionally plain:** entry/world/category names identify records; tags are comma-delimited filters. Character/Faction type/status, gender/pronouns, relationship-type labels and basic appearance values retain classification/value-entry semantics. Age/dates/height, faction founding date/membership size, population and travel duration retain calendar/measurement semantics. Existing ID selectors already express affiliations, relatives and destinations. World profile descriptions and map/pin descriptions are deferred because they have separate record/save contracts (pins also have linked-snapshot semantics).
- **Stored-length limit:** limits count the serialized token (escaped fallback name, stable ID and UUID), not just its visible chip label. A reference may not fit a 120-character field even when its displayed name is short; insertion is rejected with feedback rather than truncating it. Existing limits remain unchanged.
- **Future integration:** follow the Universal @ linking rule in AGENTS.md. Bind appropriate fields with `DescriptionLinks.bind`, collect their owner-local registries, use shared safe rendering/plain previews, and test saving/reopening, renames, missing targets and relevant backup flows. Server validation currently visits the entry, character, location, faction, creature, relationship rows, gallery rows and travel rows; new nested owners must explicitly join that validation path. Support is not automatic for new fields/categories: document exceptions and claim coverage only after implementation and tests. Desktop is the priority; mobile-specific work requires an explicit request.

`tests/universal-links.spec.js` covers representative compact/narrative insertion, row ownership, restart/rename/missing targets, Geography ZIP round trips, limits/plain emails/learned values, malformed metadata, gallery captions and rehydration/rendering of all 36 declared Character fields. The all-fields case seeds saved references; it does not individually exercise typing into every field. Shared Description/Short description behavior also has dedicated tests in `tests/description-links.spec.js` and `tests/chip-editor.spec.js`. Test contents describe coverage, not proof of a current passing run.

### Application navigation

`Navigation.visit(action)` captures the current destination/context and records a changed destination once; nested transitions are suppressed. Shared `showDetail`, category/workspace opening, Character profiles, Geography selections and map opening use it, so existing @ links and structured lore links reuse one stack. Entries are identified by stable ID; renamed entries resolve live, deleted destinations are skipped. `Navigation.suspend` / `sync` prevent save/refresh operations from creating visits. Character/Geography `state` / `restore` hooks preserve query, filters, sort, selection and collapsed hierarchy; map hooks retain canvas, pin panel, zoom and image-relative view centre. Snapshots also restore scroll positions and disclosure sections where practical.

Arrow controls live in the top bar, entry dialogs and map toolbar; their tooltips advertise the single-key shortcuts. **Q / E** navigate Back/Forward (verified in Linux Chromium); keyboard navigation is blocked in inputs, contenteditable fields and other active forms/dialogs. Clicking blank editor space moves focus out of the field, allowing Q/E through the existing dirty-editor guard. Arrow buttons in the editor reuse `Characters.closeEditor` and its existing field/image snapshot/discard confirmation, now shared across entry categories; cancelling leaves writing intact. Navigation is blocked during saves/uploads/restores. Editing is not a history destination, and saving keeps the established post-save workspace without adding a visit; Character and Location workspace profiles now reopen as reading popups. In the shared editor, Enter advances through visible, enabled text fields, skips closed groups and non-text controls, then focuses Save without submitting automatically. Shift+Enter inserts a newline in multiline fields; compact fields stay single-line. An open @ suggestion takes priority on Enter. Tab/Shift+Tab and native buttons/selects retain their normal behavior. Contenteditable line breaks use DOM BR nodes with ignored trailing padding; stored text and reference tokens are unchanged. History is in memory for this tab only: refresh, world switching and successful backup restore reset it. It does not call the browser History API or intercept browser Back/Forward. Map restoration does not re-enter native browser fullscreen. No new database/backup fields or dependencies are required. `tests/navigation.spec.js` covers history branching/states, cross-category @ links, context/scroll/map restoration, shortcuts, unsaved cancellation, edits, renames/missing entries and refresh reset.

## Library safety and current limits

Use fixture-created temporary folders or an isolated copy with `WORLDFORGE_DATA_DIR` for experiments, never the real library. Preserve the **whole** data folder across code updates. Copy it only with the server stopped (a live SQLite file alone may omit WAL transactions), or use a complete portable ZIP. For risky migration/restore work, verify backup contents/recovery in an isolated folder first; see README for rollback steps.

Not implemented: multiple independent timelines, permanent world erasure, cross-world lore links, one-click all-world ZIP backups, image overlays/layers, custom uploaded marker symbols, category deletion, rich text, pinch zoom or a standalone image gallery/cleanup. All metadata loads/saves together; large libraries may eventually need pagination/per-record APIs. Documented platform coverage is Linux/Chromium, not every OS/browser or power-loss/large-library scenario. Report actual checks per task.

Location editor: type/status accept optional free text with hints and learned values; legacy type codes still display their established labels. Optional `rulerIds`/`controllingFactionIds` arrays read legacy singular IDs when absent; saves mirror their first selection into legacy singular fields. Location-only relationship pickers keep selected colored badges visible and store neutral unlinked labels in `location.selectionNotes` keyed by relationship-list name. These short labels intentionally do not parse @ tokens or create entries; use real linked selections for references. Parent and travel destinations stay singular IDs. Validation, deletion/backlinks, search/type filters and ZIP payloads include the new lists/notes; no schema or archive version change. Characters and Factions now reuse the same flexible picker; legacy picker helpers remain for compatibility, not for new editor fields. Older app versions cannot edit these expanded relationships reliably; keep complete current ZIP backups before downgrading. Focused coverage: `tests/flexible-locations.spec.js` plus Geography regressions.

Shared card previews prioritize meaningful Short description, falling back to Description. `DescriptionLinks.preview` applies size-dependent word budgets (Small 18, Medium 40, Large 70) without cutting reference tokens/badges; visual capacity varies with width and names. Cards show up to three tags plus a remaining count. Each card is an article with a native title button and a guarded background click with sibling preview reference buttons (no nested buttons); preview links have their own pointer/keyboard targets. `CategoryColors.apply` decorates reference badges with the destination category color and configured SVG icon, including editor chips and structured links. Data formats are unchanged. Coverage: `tests/card-previews.spec.js`, card/UI and shared linking tests.

Editor relationships: `Geography.flexiblePicker` is the shared badge/search/checkbox/unlinked-note control. Character `birthplaceIds`, `homeIds`, `currentLocationIds` and Faction `headquartersIds` are optional arrays, falling back to old singular IDs on read and mirroring the first selection on save. Existing Character/Faction lists also accept owner-local `selectionNotes` keyed by list name. Character relationship rows accept optional `entryIds` plus row-owned `selectionNotes.entryIds`, retaining `entryId` as the first target and existing written notes/reference metadata. Shared `GeographyModel.validateSelectionNotes` validates bounded plain labels; these deliberately do not parse @ or create entries. Model reference/deletion helpers, profiles/backlinks and search/filter logic include the new arrays/notes. No schema/archive-version change or eager data rewrite; older app versions cannot reliably edit expanded relationships. Category selection, Location parent/travel destinations, real place-ID validation, image validation and structured numbers remain safeguarded; arbitrary wording can be added as notes. All current descriptive classifications are optional free text. Sort selects/options now explicitly use theme surface/text colors and native color-scheme. Tests: `tests/flexible-editors.spec.js` and affected category/linking suites.

Category browsing: Characters reuses the ordinary category toolbar (search, card size, New entry, sort) and section heading/count, retaining specialist filters. Future categories follow this layout unless functionality requires a specialized workspace. Locations retain the hierarchy browser. Add child location offers Create new location (parent preselected) or a single existing-location dropdown with an explicit empty state. Existing selections update only their parent and timestamp, preserve descendants/content, confirm moves from another parent, and reuse hierarchy validation/save error handling. No schema/backup changes.

Location creation requires only a nonblank name; Description and all specialist fields are optional. Browser and server validation accept empty location descriptions, including backup restore; other category requirements and validation of supplied optional values remain. No schema/archive change. Shared dialog `.form-error` summaries are placed beneath their heading and scrolled into view on errors, including native invalid controls; entry field-limit feedback also uses the top summary.

History Phase 1: optional `entry.history` JSON stores `startDate`/`endDate` as null or `{year, precision:"year"}`, plus optional `dateCertainty` (open text; confirmed/approximate/disputed/unknown are canonical suggested values), `calendar` (120 characters), and `eventType` (120 characters; predefined codes or custom wording). Years retain the existing integer range −999999…999999; explicit zero is allowed, empty never becomes zero, and no JavaScript Date parsing/calendar conversion is used. New optional fields need no SQLite/API/ZIP version change or bulk migration. Reads of absent startDate fall back to legacy `year`; explicit null stays unpositioned. Non-chronology edits of legacy entries leave history absent. Chronology edits mirror startDate.year to legacy year, or `""` for no start; server/restore validation rejects disagreement, invalid years/precision, reversed ranges and dates supplied with Unknown certainty. Unknown certainty saves null dates and an empty legacy year, retaining typed years only in the unsaved editor if the user switches certainty back. Missing endDate never implies a duration.

History reuses shared title/descriptions/@ links, image, tags, collapsible form sections, top error summary, keyboard/discard handling and reading fields. Event type is an open classification input with native suggestions (all 12 requested types plus saved custom values).
